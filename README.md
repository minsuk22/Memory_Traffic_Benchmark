# MemTraffic Bench — GPU-generated DRAM traffic benchmark for Android

Measures how fast a mobile SoC's memory system can serve **pure DRAM reads, writes and copies**,
with all traffic generated by the GPU shader cores (Vulkan compute). Each invocation produces its
own pseudo-random addresses from a runtime key, so neither the shader compiler nor the driver
can predict, merge or skip the accesses. Every result is checked against a CPU reference.

```
native/
  shaders/common.glsl   hash, bijective address permutation, checksum, push constants
  shaders/read.comp     random/sequential read  -> checksum   (SINK=0: dead-code control)
  shaders/write.comp    random/sequential write of seed-dependent data (also used to fill)
  shaders/copy.comp     random/sequential copy (lower half -> upper half of each chunk)
  shaders/verify.comp   untimed full-content verification
  src/membench.cpp      Vulkan host code, tests, anti-optimisation checks, report
  src/reference.h       bit-exact CPU mirror of the shader math
  src/main_cli.cpp      adb-shell executable
  src/jni_bridge.cpp    JNI for the app
app/                    minimal Android app (same native code)
scripts/                setup / build / run (PowerShell)
```

## 2. Build & run

**CLI (recommended for measurements)**

```powershell
scripts\build_cli.ps1                                # -> build\android-cli\membench (arm64)

```

**APK**

```powershell

```

Options (`membench --help`):

| option | default | meaning |
|---|---|---|
| `--size-mb N` | 1024 | total working set (split into chunks <= 256 MiB) |
| `--line N` | 64 | bytes fetched per random address (16..4096). 64 B = one cache line / DRAM burst |
| `--tests` | read,write,copy | which traffic types |
| `--pattern` | both | `rand`, `seq` or `both` (sequential = reference for the random numbers) |
| `--reps / --warmup` | 5 / 2 | measured / minimum discarded repetitions per test |
| `--warmup-ms N` | 500 | warm-up also lasts at least this much GPU time per test |
| `--prewarm-ms N` | 2000 | GPU/DRAM load before the first test so the clocks ramp up (0 = off) |
| `--boost MODE` | both | `cpu`, `gpu`, `both` or `off`: load right before the tests to raise the DVFS clocks; `gpu` runs 1024³ GEMMs on the matrix units (`VK_KHR_cooperative_matrix`, fp32 shader GEMM as fallback) |
| `--boost-ms N` | 3000 | duration of the boost load |
| `--peak-gbps X` | – | theoretical DRAM peak; any result above it is a FAIL (traffic did not reach DRAM) |
| `--sweep` | off | working-set sweep 64 KiB → chunk size: shows the cache → DRAM cliff |
| `--seed N` | random | reproduce a run exactly |
| `--no-cpu-ref` | – | skip CPU reference checksums (faster, weaker) |
| `--inject-fault` | – | self-test: kernels silently skip part of their work → the checks must FAIL |

The theoretical peak is `transfer rate x bus width`, e.g. LPDDR5X-8533 x 64 bit = 68.3 GB/s,
LPDDR5-6400 x 64 bit = 51.2 GB/s.

## 3. How the traffic is generated

* **Memory content:** word `w` holds `hash32(w ^ hash32(seed))`, written by the GPU from a
  runtime seed. Nobody (compiler, driver) can know it in advance.
* **Addresses:** the line index goes through a 4-round **bijective permutation** (xor key →
  multiply by odd constant mod 2^n → xorshift) keyed per chunk and per pass by push constants.
  Every invocation therefore reads/writes different, unpredictable addresses, yet every line is
  touched **exactly once per pass**: no reuse, no cache hits, deterministic results.
* **Granularity:** `line/16` neighbouring invocations fetch one line together (16 B each), so a
  64 B line is one coalesced request. Each invocation keeps 4 independent loads in flight per
  iteration; 256 K invocations per dispatch.
* **Footprint:** default 1 GiB, far larger than GPU L2 + system-level cache (a few MiB to ~16 MiB).
* **Checksum:** wrap-around sum of `mix(value, logical index)`. It is order independent
  (scheduling does not matter) but changes if any load is skipped, returns stale data or hits the
  wrong address. Each workgroup also counts itself, so missing workgroups are detected.

## 4. How it proves nothing was optimised away

| # | check | what it proves |
|---|---|---|
| 1 | GPU checksum == CPU reference (every run) | every one of the N loads happened, at the right address, and returned the real data |
| 2 | identical checksum across repeated runs | deterministic; no races or partial execution |
| 3 | other key → different checksum, still == CPU | the result is not cached / constant-folded |
| 4 | **dead-code control**: same kernel with the result discarded | shows what "optimised away" looks like on this driver (usually ~0 ms). The real kernel takes orders of magnitude longer → its loads were *not* removed |
| 5 | 2 passes take ~2x the time of 1 pass | work is neither skipped nor merged |
| 6 | cache-resident footprint is much faster than the 1 GiB run | the kernel is memory-bound, not ALU-bound, so the DRAM number is a real memory limit |
| 7 | write/copy: full content verified after every run (new seed / keys each run) | every write reached memory; stale results would fail |
| 8 | read-after-write vs CPU | written data is correct through an independent read path |
| 9 | `--peak-gbps`: result <= physical DRAM peak | traffic was not served by a cache |
| 10 | driver pipeline statistics (if `VK_KHR_pipeline_executable_properties`) | e.g. register count of real vs control kernel |
| – | `build/*/generated/*.spvasm` | SPIR-V disassembly: the loads/stores are in the loop given to the driver |
| – | `--inject-fault` | the checks themselves catch a kernel that skips work |

For external confirmation, measure the DRAM counters during a run with the vendor profilers
(Snapdragon Profiler / Perfetto GPU counters on Adreno, Arm Streamline on Mali): the DRAM read
bytes should equal the reported traffic (for 64 B lines).

## 5. Interpreting results

* `READ rand` vs `READ seq`: random 64 B accesses lose row-buffer locality and pay page-table
  walks (TLB misses), so they are typically well below sequential bandwidth. Larger `--line`
  (128/256 B) moves toward sequential behaviour; `--line 16` shows the cost of sub-burst accesses
  (the DRAM still transfers whole bursts, so useful bandwidth drops).
* `COPY` reports read + write bytes.
* Mobile GPUs ramp clocks and throttle: look at the median, run a few times, let the phone
  cool down, keep it plugged in, screen on.
* Warm-up: a 2 s pre-warm (sequential + random reads with a separate permutation key), then
  per test at least 2 runs and 500 ms of GPU time are discarded. The CPU reference checksum is
  computed during the warm-up so the GPU never idles before the measured runs. Warm-up cannot
  leave useful data in the caches: each run touches the whole set (>> cache size) once, so at
  most a few MiB of the last run survive. A run-to-run spread above 10 % gives a WARN.
* Boost: after the pre-warm, all CPU cores run integer hashing and the GPU runs back-to-back
  1024³ GEMMs (fp16 on the matrix units via `VK_KHR_cooperative_matrix`, else an fp32 shader
  GEMM; the result is checked) for 3 s, so DVFS governors that follow CPU/GPU load raise the
  memory-interface clocks. `probe before boost` / `probe after boost` in the log show the
  effect on read bandwidth. On SoCs where CPU and GPU share one power budget the CPU load can
  also *lower* the GPU clocks afterwards; compare `--boost gpu`, `--boost cpu` and `--boost off`.
* Timing uses GPU timestamps (falls back to CPU wall time when the queue has none).

## 6. Results

### Galaxy S24+ (SM-S926N, Exynos 2400 / Xclipse 940, LPDDR5X-8533 x64 = 68.3 GB/s peak)

`--size-mb 1024 --sweep --peak-gbps 68.3` — 15/15 checks PASS (`results/SM-S926N_*.txt`)

| test (64 B) | median GB/s |
|---|---|
| READ seq | 43.0 (63 % of peak) |
| WRITE seq | 39.6 |
| COPY seq (R+W) | 38.6 |
| READ rand | 2.66 |
| WRITE rand | 2.58 |
| COPY rand (R+W) | 2.62 |

Dead-code control 0.03 ms vs 403 ms (VGPR 28 → 3), 2-pass scaling x2.00, cache-resident run x65.

Working-set sweep (random read): ~218 GB/s up to 1 MiB (GPU L2), ~42 GB/s from 4 MiB to
64 MiB, then **10.7 GB/s at 128 MiB and 2.9 GB/s at 256 MiB**. Random read vs access size
(1 GiB set):

| line | GB/s | accesses/s |
|---|---|---|
| 64 B | 3.1 | 48 M |
| 256 B | 11.9 | 46 M |
| 1 KiB | 31.1 | 30 M |
| 4 KiB | 44.5 | 11 M |

The rate is bounded by *accesses* (~47 M/s), not bytes, once the footprint exceeds ~64 MiB:
random accesses over large footprints are limited by GPU address translation (TLB misses /
page-table walks), not by DRAM bandwidth. Use the sweep to separate the two: the 4–64 MiB
plateau is DRAM with TLB hits, the >64 MiB region adds translation cost.
