# MemTraffic Bench — GPU-generated DRAM traffic benchmark for Android

Measures how fast a mobile SoC's memory system can serve **pure DRAM reads, writes and copies**,
with all traffic generated by the GPU shader cores (Vulkan compute). Each invocation produces its
own pseudo-random addresses from a runtime key, so neither the shader compiler nor the driver
can predict, merge or skip the accesses. Every result is checked against a CPU reference.

```
native/
  shaders/common.glsl   hash, bijective address permutation, checksum, push constants
  shaders/read.comp     random/sequential read  -> checksum   (SINK=0: dead-code control)
  shaders/write.comp    random/sequential write of seed-dependent data (also used to fill)
  shaders/copy.comp     random/sequential copy (lower half -> upper half of each chunk)
  shaders/verify.comp   untimed full-content verification
  src/membench.cpp      Vulkan host code, tests, anti-optimisation checks, report
  src/reference.h       bit-exact CPU mirror of the shader math
  src/main_cli.cpp      adb-shell executable
  src/jni_bridge.cpp    JNI for the app
app/                    minimal Android app (same native code)
scripts/                setup / build / run (PowerShell)
```

Options (`membench --help`):

| option | default | meaning |
|---|---|---|
| `--size-mb N` | 1024 | total working set (split into chunks <= 256 MiB) |
| `--window-mb N` | – | random accesses stay inside N MiB windows, one at a time (no GPU TLB misses, e.g. 64) |
| `--line N` | 64 | bytes fetched per random address (16..4096). 64 B = one cache line / DRAM burst |
| `--tests` | read,write,copy | which traffic types |
| `--pattern` | both | `rand`, `seq` or `both` (sequential = reference for the random numbers) |
| `--reps / --warmup` | 5 / 2 | measured / minimum discarded repetitions per test |
| `--warmup-ms N` | 500 | warm-up also lasts at least this much GPU time per test |
| `--prewarm-ms N` | 2000 | GPU/DRAM load before the first test so the clocks ramp up (0 = off) |
| `--boost MODE` | both | `cpu`, `gpu`, `both` or `off`: load right before the tests to raise the DVFS clocks; `gpu` runs 1024³ GEMMs on the matrix units (`VK_KHR_cooperative_matrix`, fp32 shader GEMM as fallback) |
| `--boost-ms N` | 3000 | duration of the boost load |
| `--peak-gbps X` | – | theoretical DRAM peak; any result above it is a FAIL (traffic did not reach DRAM) |
| `--sweep` | off | working-set sweep 64 KiB → chunk size: shows the cache → DRAM cliff |
| `--peak` | off | peak finder (~2.5 min, see below) instead of the normal tests |
| `--cpu` | off | CPU random read peak (see below) instead of the normal tests |
| `--dvfs` | off | random read vs memory clock governors (see below) instead of the normal tests |
| `--matrix` | off | random read feeding matrix multiplies (see below) instead of the normal tests |
| `--rand-tune` | off | random read tuning inside a TLB-sized window (see below) instead of the normal tests |
| `--seed N` | random | reproduce a run exactly |
| `--no-cpu-ref` | – | skip CPU reference checksums (faster, weaker) |
| `--inject-fault` | – | self-test: kernels silently skip part of their work → the checks must FAIL |

The theoretical peak is `transfer rate x bus width`, e.g. LPDDR5X-8533 x 64 bit = 68.3 GB/s,
LPDDR5-6400 x 64 bit = 51.2 GB/s.

## 3. How the traffic is generated

* **Memory content:** word `w` holds `hash32(w ^ hash32(seed))`, written by the GPU from a
  runtime seed. Nobody (compiler, driver) can know it in advance.
* **Addresses:** the line index goes through a 4-round **bijective permutation** (xor key →
  multiply by odd constant mod 2^n → xorshift) keyed per chunk and per pass by push constants.
  Every invocation therefore reads/writes different, unpredictable addresses, yet every line is
  touched **exactly once per pass**: no reuse, no cache hits, deterministic results.
* **Granularity:** `line/16` neighbouring invocations fetch one line together (16 B each), so a
  64 B line is one coalesced request. Each invocation keeps 4 independent loads in flight per
  iteration; 256 K invocations per dispatch.
* **Footprint:** default 1 GiB, far larger than GPU L2 + system-level cache (a few MiB to ~16 MiB).
* **Checksum:** wrap-around sum of `mix(value, logical index)`. It is order independent
  (scheduling does not matter) but changes if any load is skipped, returns stale data or hits the
  wrong address. Each workgroup also counts itself, so missing workgroups are detected.

## 4. How it proves nothing was optimised away

| # | check | what it proves |
|---|---|---|
| 1 | GPU checksum == CPU reference (every run) | every one of the N loads happened, at the right address, and returned the real data |
| 2 | identical checksum across repeated runs | deterministic; no races or partial execution |
| 3 | other key → different checksum, still == CPU | the result is not cached / constant-folded |
| 4 | **dead-code control**: same kernel with the result discarded | shows what "optimised away" looks like on this driver (usually ~0 ms). The real kernel takes orders of magnitude longer → its loads were *not* removed |
| 5 | 2 passes take ~2x the time of 1 pass | work is neither skipped nor merged |
| 6 | cache-resident footprint is much faster than the 1 GiB run | the kernel is memory-bound, not ALU-bound, so the DRAM number is a real memory limit |
| 7 | write/copy: full content verified after every run (new seed / keys each run) | every write reached memory; stale results would fail |
| 8 | read-after-write vs CPU | written data is correct through an independent read path |
| 9 | `--peak-gbps`: result <= physical DRAM peak | traffic was not served by a cache |
| 10 | driver pipeline statistics (if `VK_KHR_pipeline_executable_properties`) | e.g. register count of real vs control kernel |
| – | `build/*/generated/*.spvasm` | SPIR-V disassembly: the loads/stores are in the loop given to the driver |
| – | `--inject-fault` | the checks themselves catch a kernel that skips work |

For external confirmation, measure the DRAM counters during a run with the vendor profilers
(Snapdragon Profiler / Perfetto GPU counters on Adreno, Arm Streamline on Mali): the DRAM read
bytes should equal the reported traffic (for 64 B lines).

## 5. Interpreting results

* `READ rand` vs `READ seq`: random 64 B accesses lose row-buffer locality and pay page-table
  walks (TLB misses), so they are typically well below sequential bandwidth. Larger `--line`
  (128/256 B) moves toward sequential behaviour; `--line 16` shows the cost of sub-burst accesses
  (the DRAM still transfers whole bursts, so useful bandwidth drops).
* `COPY` reports read + write bytes.
* Mobile GPUs ramp clocks and throttle: look at the median, run a few times, let the phone
  cool down, keep it plugged in, screen on.
* Warm-up: a 2 s pre-warm (sequential + random reads with a separate permutation key), then
  per test at least 2 runs and 500 ms of GPU time are discarded. The CPU reference checksum is
  computed during the warm-up so the GPU never idles before the measured runs. Warm-up cannot
  leave useful data in the caches: each run touches the whole set (>> cache size) once, so at
  most a few MiB of the last run survive. A run-to-run spread above 10 % gives a WARN.
* Boost: after the pre-warm, all CPU cores run integer hashing and the GPU runs back-to-back
  1024³ GEMMs (fp16 on the matrix units via `VK_KHR_cooperative_matrix`, else an fp32 shader
  GEMM; the result is checked) for 3 s, so DVFS governors that follow CPU/GPU load raise the
  memory-interface clocks. `probe before boost` / `probe after boost` in the log show the
  effect on read bandwidth. On SoCs where CPU and GPU share one power budget the CPU load can
  also *lower* the GPU clocks afterwards; compare `--boost gpu`, `--boost cpu` and `--boost off`.
* Timing uses GPU timestamps (falls back to CPU wall time when the queue has none).
* Peak finder (`--peak`, or the **Peak finder** button in the app; needs no adb, so it also
  works on MDM-managed phones — **Share log** / **Copy log** export the output, and every run
  is also saved to `Download/membench/membench_<date>_<time>.txt`, readable over USB file transfer):
  1. cold read probe + multi-threaded CPU memcpy (first measurements of the process),
  2. 8 s of continuous sequential reads, bandwidth per second (does it ramp up?),
  3. READ seq over workgroup size {64..1024} x invocations {64K, 256K, 1M},
  4. READ rand over workgroup size x invocations, then access size 64 B..4 KiB,
  5. WRITE / COPY seq with the best configuration; best read configurations checked
     against the CPU reference,
  6. the working set is freed and allocated again in the same process (is the slow state
     tied to the memory the process got first?),
  7. 15 s idle, probe again, CPU memcpy again,
  8. the CPU random read below.

  It ends with the peak numbers, the options that reach them (`--wg`, `--threads`) and a
  short diagnosis. Run it once after the phone has been idle and once right afterwards to
  compare a first run with a second one.
* CPU random read (`--cpu`, app button **CPU random**): the CPU reads the *same* job as the
  GPU random read — same data, same permuted addresses, same checksum — from a host buffer of
  the same size (the GPU working set is freed first). Its checksum must equal the GPU's and the
  formula's. It reports threads x software-prefetch distance, access size, a footprint sweep
  (GPU and CPU bandwidth plus dependent-load CPU latency) and a run with `MADV_HUGEPAGE`. The
  smallest footprint is cache resident, so its CPU number is the compute ceiling of the
  address + checksum loop.
* Random read vs clock governors (`--dvfs`, app button **Rand vs DVFS**, ~1 min): the DDR /
  bus governors pick the memory clocks from the *measured bandwidth*, and a random read moves
  few bytes per second, so it may run at low memory clocks. The same verified random read is
  measured
  * **A** while 1..all CPU cores stream-read another 256 MiB buffer (idle again at the end),
  * **B** split into 16 slices per chunk with GPU sequential reads of 16 MiB .. 256 MiB between
    the slices (one submission, every random slice timed on the GPU, slices together must
    give the CPU reference checksum),
  * **C** over footprints 16 MiB .. 1 GiB, idle / with background load / idle again.

  A large gain in A or B means the governors limit the random read; a footprint cliff that
  stays with the clocks up means GPU address translation (TLB reach) does. Clock files
  (`/sys/class/devfreq/*/cur_freq`, kgsl `gpuclk`) are sampled when the app may read them.
* Random read + matrix math (`--matrix`, app button **Rand + matrix**): kernels that load
  exactly like `read.comp` (same verified checksum) and use every loaded byte as matrix data —
  `coopMatMulAdd` on the matrix units with `VK_KHR_cooperative_matrix`
  (`shaders/randmm_coop.glsl`), 4x4 fp32 matrices on the ALUs otherwise
  (`shaders/randmm_alu.comp`). The matrix work is swept from 0 to 64 reps (16 flop per loaded
  byte per rep) at 1 MiB (cache resident = compute ceiling), 64 MiB and the whole set. If the
  whole-set column stays flat while GFLOP/s grows, the GPU cores are waiting for memory, not
  limiting the random read.
* Random read inside the TLB reach (`--window-mb N`, app button **Rand in 64 MiB**): the working
  set is split into N MiB chunks, every random pass stays inside one chunk and the chunks run
  one after another (barrier between them), so at most N MiB are accessed randomly at any time
  while the whole set is still read once per pass. Choose N below the footprint where the
  `--dvfs` sweep falls off (Adreno 830: 64 MiB). This is the random-read bandwidth without GPU
  address-translation misses; the normal run (256 MiB chunks) includes them.
* Random read tuning (`--rand-tune`, app button **Rand tuning**, ~1 min): a greedy search
  that varies one factor at a time and keeps the best value (> 3 % better, candidates measured
  round-robin), in this order:
  1. window size 1 MiB .. chunk (first: above the GPU TLB reach every other knob is hidden);
  2. **rolling windows**: one dispatch per chunk, workgroup `g` works on window `g / G`, so with
     workgroups started roughly in ID order only a few windows are active at a time — a small
     footprint without a barrier and pipeline drain after every window;
  3. invocations, workgroup size, random lines in flight per invocation (`UNROLL` 1..16),
     bytes per lane (16 / 32 / 64 B), storage vs uniform texel buffer, subgroup size;
  4. window again, memory allocation (every device-local type, default type twice, one
     allocation for the whole set), and — information only — the access size 32..256 B.

  **Cache-line reuse guard:** a small window could look fast only because the memory system
  fetches 128 B and the other 64 B are hit in a cache later. The tuner therefore also reads
  only one 64 B line per 128 B block (same lines in flight per invocation); if that is > 10 %
  slower, windows below 4 MiB are not used (WARN). Every line of the set is read exactly once
  per run, every timed run is checked against the CPU reference. Kernel: `shaders/read_tune.glsl`.

## 6. Results

### Galaxy S25 Ultra (SM-S938N, Snapdragon 8 Elite / Adreno 830, driver 0x80320040)

`--size-mb 1024 --rand-tune` in the app (v1.11, `results/SM-S938N_rand_tune.txt`) — 3/3 checks PASS

| random 64 B read | GB/s | % of READ seq (67.4) |
|---|---|---|
| 64 MiB windows, one at a time (v1.8 shape) | 31.7 | 47 % (TLB reach 64..128 MiB) |
| 1 MiB rolling windows, v1.8 kernel shape (wg 256, unroll 4) | 45.3 | 68 % |
| **1 MiB rolling, wg 64, unroll 16** | **57.5** | **85 %** |
| 1 MiB rolling, one line per 128 B (reuse guard) | 55.1 | 0.96 of dense → no cache-line reuse |

Unlike the Adreno 730, the Adreno 830 also profits from the kernel shape once the window is
small: small workgroups (64) and 16 random lines in flight per invocation (+27 %).

### Galaxy S22 Ultra (SM-S908N, Snapdragon 8 Gen 1 / Adreno 730, LPDDR5-6400 x64 = 51.2 GB/s peak)

`--size-mb 1024 --rand-tune` (v1.11, `results/SM-S908N_rand_tune.txt`) — all runs verified

| random 64 B read | GB/s | % of READ seq (47.5) |
|---|---|---|
| 64 MiB windows, one at a time (v1.8 shape) | 6.2 | 13 % (GPU TLB misses: reach 32..64 MiB) |
| 4 MiB windows, one at a time | 29 | 63 % |
| 4 MiB rolling windows | 30 | 65 % |
| **1 MiB rolling windows** | **36.4 – 36.6** | **75 – 77 %** |
| 1 MiB rolling, one line per 128 B (reuse guard) | 34–35 | 0.93 – 1.05 of dense → no cache-line reuse |

No kernel shape knob (invocations, workgroup, unroll, bytes per lane, texel path, subgroup
size, memory type) moves the number by more than noise once the window is right; random
128 B lines reach ~100 % of sequential. The random-read limit on this GPU is the number of
pages touched at a time (address translation), not DRAM.

**Driver issue found on this phone:** inside the app (not in the adb CLI), two back-to-back
independent dispatches in one command buffer sometimes came out completely wrong — always
two consecutive 128 MiB chunks, in every 1 GiB run, also with v1.8 and with one allocation for
the whole set. The initial content check caught it (`[FAIL] initial memory content`). Since
v1.11 every chunk dispatch is separated by a compute→compute barrier (a few µs per run),
which fixes it; a failed content check now also lists the wrong chunks and fills once more.

### Galaxy S24+ (SM-S926N, Exynos 2400 / Xclipse 940, LPDDR5X-8533 x64 = 68.3 GB/s peak)

`--size-mb 1024 --sweep --peak-gbps 68.3` — 15/15 checks PASS (`results/SM-S926N_*.txt`)

| test (64 B) | median GB/s |
|---|---|
| READ seq | 43.0 (63 % of peak) |
| WRITE seq | 39.6 |
| COPY seq (R+W) | 38.6 |
| READ rand | 2.66 |
| WRITE rand | 2.58 |
| COPY rand (R+W) | 2.62 |

Dead-code control 0.03 ms vs 403 ms (VGPR 28 → 3), 2-pass scaling x2.00, cache-resident run x65.

Working-set sweep (random read): ~218 GB/s up to 1 MiB (GPU L2), ~42 GB/s from 4 MiB to
64 MiB, then **10.7 GB/s at 128 MiB and 2.9 GB/s at 256 MiB**. Random read vs access size
(1 GiB set):

| line | GB/s | accesses/s |
|---|---|---|
| 64 B | 3.1 | 48 M |
| 256 B | 11.9 | 46 M |
| 1 KiB | 31.1 | 30 M |
| 4 KiB | 44.5 | 11 M |

The rate is bounded by *accesses* (~47 M/s), not bytes, once the footprint exceeds ~64 MiB:
random accesses over large footprints are limited by GPU address translation (TLB misses /
page-table walks), not by DRAM bandwidth. Use the sweep to separate the two: the 4–64 MiB
plateau is DRAM with TLB hits, the >64 MiB region adds translation cost.
